# dsh-mishu 调研与设计

> 2026-10-21 重写，取代 10-20 的初稿。写代码前先读完这份。

## 一句话

**dsh-mishu（DSH 小秘书）**：替你处理所有待处理事项的提醒。简单的它直接处理，复杂的告诉你。

它从 GitHub、邮箱、飞书等地方**往里收**消息，判断哪些真要你处理。市场上几百个"通知插件"做的是 DSH 跑完任务后**往外推**，方向正好相反。

## 已经定下的取舍

- **本本分分做秘书。**只做秘书该做的事，不往更大的方向扩。
- **邮件代码自己写，不依赖第三方邮件插件。**邮件涉及隐私，业务逻辑必须是自己能审查的代码。协议层用成熟的开源库（见"邮件"一节）。
- **推送自己写**，不依赖其他插件（见"提醒和推送"一节）。
- **模型**：默认跟随 DSH 当前用的模型，另外可以选本地模型（Ollama 等）。

## 为什么做：一个典型的通知箱

一个维护十来个仓库的开发者，GitHub 上积了几十条未读通知，**真正要处理的只有一两件**。其余的，查一下对象的**当前状态**就能判断（下表的仓库名都是举例）：

| 通知 | 实际情况 | 结论（理由码） |
|---|---|---|
| fork `example-org/demo-fork` 每天好几个工作流失败 | 这是个 fork，没有自己的提交，跑的是上游的定时工作流 | 每条单看都是噪音；**合起来是一件要做的事：关掉这个 fork 的 Actions，或者删掉 fork**（`fork-upstream-schedule`） |
| 你提给上游的几个 PR | 全部已合并 | 已完结（`merged`） |
| 机器人开的"兼容性检查失败"issue | 后续一轮通过，bot 已自动关闭 | 已完结（`closed`） |
| 一串旧版本 tag 的 CI 失败 | 都是旧 tag，main 和最新版本都是绿的 | 已被取代（`superseded`） |
| 某次 Release 失败 | 下一个版本就修好了 | 已被取代（`superseded`） |
| main 上失败了几次 | 之后通过了 | 已恢复（`recovered`） |

从这个例子能看出两件事：

1. **判断靠的不是通知文字，而是对象现在的状态**：PR 合没合、issue 关没关、同一工作流在同一分支上最近一次跑的结果。
2. **要做的事可能藏在一堆噪音里。**同一个来源持续制造噪音，这件事本身就该变成一个待办。

这些情况就是第一版的回归用例（见"测试数据"一节）。

## 核心模型：事项，不是消息

秘书管的是**事项**，消息只是证据。

- 一个事项可以由很多条消息组成：fork 每天 3 条失败通知是一件事；同一件事的邮件和 GitHub issue 也合成一件。
- 事项的生命周期：**待我处理 → 等别人 → 已完成 / 已忽略**。
- 每条消息对事项的作用只有三种：**新建、更新、关闭**。PR 合并了、CI 变绿了，对应的事项就自动关闭。
- 有些待办根本没人发消息提醒你，比如证书和域名快到期、账单要交、你发出的邮件三天没人回。这类要靠**主动检查**来产生（第一版不做）。
- 事项有了新动态，即使你已经处理过，也重新冒出来（照 Octobox 的做法）。

你看到的是"现在有哪些事"，不是"来了哪些消息"。

## 流程

```
来源适配器：拉取，按游标增量
  → 补全：查对象的当前状态（PR/issue/CI），按 subject 和 updated_at 缓存
  → 归并：去重、聚合成事项
  → 规则判断（带理由码）→ 规则判断不了的交给模型（附理由）
  → 授权策略：决定 L0–L3 各怎么处理
  → 执行：写操作日志，可撤销
  → 提醒：只在事项有变化时提醒
```

每个来源适配器实现同一套接口：拉取、补全、列出可执行的动作和它们的风险级别。以后加来源，只需要写新的适配器。

## 分诊：规则在前，模型在后

- 每个判断都带**理由码**（`merged`、`closed`、`superseded`、`recovered`、`fork-upstream-schedule` 等）。你扫一眼理由，就知道这个判断能不能信。
- 规则覆盖能确定的情况；规则判断不了的交给模型，模型要给出理由。
- **安全底线：触发动作的只能是规则和结构化状态，不能是消息内容。**邮件内容是陌生人能控制的，比如有人写"请把发票转到 xxx"。模型可以分类、总结、提建议，但它根据内容提出的动作一律要你确认。2025 年已经有论文演示过用特制邮件劫持 LLM 邮件代理。

## 动作分级

| 级别 | 例子 | 默认 |
|---|---|---|
| L0 只动 mishu 自己 | 在 mishu 里归档、合并、关闭事项 | 自动 |
| L1 可撤销、只影响你自己 | GitHub 通知标已读、邮件标已读或挪进文件夹 | 要确认；同类操作你批准过几次后，提议改成自动 |
| L2 对外但风险低 | 关 fork 的 Actions、重跑 CI、退订邮件列表 | 每次一键确认 |
| L3 代表你说话，或不可撤销 | 回邮件、发消息、付款、删除 | 永不自动，只起草 |

所有自动执行的操作都记日志，并且能撤销。

## 已读状态怎么处理

### 依据

| 来源 | 发现 | 结论 |
|---|---|---|
| Whittaker & Sidner 1996 "Email Overload"，以及 2006、2014 年的复现研究 | 人们把收件箱当待办清单用，未读状态是给自己留的提醒 | 自动改已读，等于替用户删提醒 |
| 微软 Outlook 用 Focused Inbox 取代 Clutter | Clutter 把邮件挪进另一个文件夹，用户经常忘了看，导致漏信 | 可以折叠，不能让东西消失 |
| SaneBox | 把邮件挪进 @SaneLater，每天发一份"过滤掉了什么"的摘要，从用户的纠正里学习 | 折叠 + 摘要 + 学习纠正 |
| HEY Screener | 陌生发件人第一次来信时由用户决定，以后对这个人永久生效 | 按发件人问一次，以后自动 |
| Octobox | 自己维护"已归档"状态，不改 GitHub 的已读状态；有新动态自动恢复；同步标已读要用户手动操作 | mishu 照这个模型做 |
| Parasuraman & Riley 1997 | 误报多了，人会弃用自动化；过度信任，人会漏掉自动化犯的错 | 误报和漏报都要盯着 |
| Parasuraman, Sheridan & Wickens 2000 | 收集和分析信息可以高度自动化，执行动作在后果严重时要保守 | 拉取和分析全自动，动作分级 |
| Horvitz 1999 | 只有当自主行动的期望收益高于"不做"或"先问"时才该自己动手 | 自不自动，看判错的代价 |

### 做法

判错的代价不对称：把重要的东西标成已读，代价远大于让一条噪音多留一会儿。所以分三层：

1. **mishu 自己的"已处理"状态：全自动。**不动来源端，有新动态就自动恢复。
2. **同步到 GitHub 标已读（`PATCH /notifications/threads/{id}`）：按规则逐条开启。**只对查过当前状态、判断确定的规则开放，比如"PR 已合并，之后没有 @你"、"同一分支后来已经成功"。开启前先跑**影子模式**：只显示"开了会标哪些"，你抽查过没问题再打开。
3. **邮件：默认不碰已读状态。**只在 mishu 里折叠，并在摘要里列出折叠了什么。你可以按发件人做一次决定（"这个人的邮件以后自动标已读"），之后自动执行。**模型的判断永远不直接改来源端。**垃圾邮件交给邮件服务商的垃圾箱，mishu 不扫垃圾箱。

**纠错统计**：你每从折叠里捞回一条，就给对应的规则记一次判错。判错率超过阈值的规则自动降级。

## 提醒和推送

### 节奏

- Fitz 等 2019 年做过一个 237 人的随机实验：每天集中推送 3 次，压力下降、幸福感上升；每小时推一次几乎没有效果；完全不推反而更焦虑。
- Google SRE 的原则是"每条告警都必须需要人来处理"。
- 所以：**紧急且要你处理的立刻推**，其余每天分 3 次汇总推，有安静时段，只在事项有变化时推。

### 内容

- 默认只推事项标题，不推邮件正文，细节回到 DSH 里看。
- 从手机点按钮确认动作时，要校验点击者是你本人（飞书 open_id、Telegram chat id 白名单）。
- L3 级动作在手机上也只能看草稿，不能执行。

### 渠道

**不自己做 App。**做 App 要苹果开发者账号、APNs 推送证书、转发服务器，还要过审核；安卓还得再做一套。转发服务器也会经手所有用户的提醒内容，隐私责任更大。

**渠道用现成的，发送代码自己写。**每个渠道本质上就是一个 HTTPS 请求，不引入第三方推送库。

| 渠道 | 手机上能点按钮确认 | 需要公网 IP | 隐私 | 评价 |
|---|---|---|---|---|
| 飞书机器人（自建应用 + 长连接） | ✅ 交互卡片 | 不需要 | 内容经过飞书服务器 | 国内首选；飞书本来就要接，一套凭据既读又推 |
| Telegram bot | ✅ 消息内按钮 | 不需要（长轮询） | 不是端到端加密 | 海外首选；国内要翻墙 |
| Bark（只有 iOS） | ❌ | 可以自建服务器 | 支持端到端加密 | 适合只推最少内容 |
| ntfy | 有限 | 可以自建 | 自建时 iOS 推送仍经 ntfy.sh 中转 | 安卓可选 |
| 微信 | — | — | — | 最难：个人微信没有官方机器人接口；企业微信推到微信据说新应用受限、要配可信 IP（未核实）；Server酱 是第三方中转 |

**待定**：用哪几个渠道，取决于你的手机系统和常用通讯软件。初步建议是飞书 + Bark，Telegram 作为第三个。

## 邮件

- **只读接入**：IMAP 用 `EXAMINE` 打开邮箱，而不是 `SELECT`，拉取邮件不会改变已读状态。
- **协议层用开源库**：`imapflow` 和 `mailparser`（Nodemailer 作者维护，MIT 协议）。从零手写 IMAP 和 MIME 解析，出 bug 的地方反而更多。业务逻辑全部自己写。
- **先看邮件头**：`List-Unsubscribe` / `List-Id` 是订阅邮件；`Auto-Submitted` 和 noreply 发件人是系统邮件；验证码过几分钟就没用了。
- **规则示例**：
  - 直接发给你（在 To 里，不是 CC）、最后一封来自对方、发件人是你写过信的人 → 待回复
  - 你发的最后一封，N 天没回复 → 提醒你跟进
  - 日历邀请 → 待回应
  - 账单 → 带截止日期的事项
- **送模型的内容要可控**：只有规则判断不了的才送，默认只送邮件头和摘要；可以设"永不送模型"的发件人或域名（银行、医疗等）。选了本地模型，就不出本机。
- **本地只存元数据和摘要**，正文需要时再取。

## 存储与凭据

- 本地 SQLite（用 Node 内置的 `node:sqlite`，不引入原生依赖）。存事项、消息元数据、摘要、规则统计和操作日志。
- **GitHub token**：先读环境变量；没有就用你在设置页填的 token（先到 GitHub 检查能不能读通知，再存系统钥匙串，条目名 `github`）；再没有就用 `gh auth token`（GitHub CLI 存在系统钥匙串里的那个）。`gh`、`security`、`secret-tool`、PowerShell 都按完整路径找：先找 PATH，再找 Homebrew、`~/.local/bin`、winget、Scoop 等常见位置，因为从 Dock/开始菜单启动的程序拿到的 PATH 往往很短。
- **邮箱授权码（以后的飞书 app secret 同样）**：存系统钥匙串，服务名 `dsh-mishu`，条目名 `mail:<编号>`。macOS 用 `security`，Windows 用 PowerShell 调 `Windows.Security.Credentials.PasswordVault`，Linux 用 `secret-tool`。密码只通过标准输入交给这些程序，不出现在命令行参数里（同机的其他进程能看到参数）。没有钥匙串时，设置页写明原因（比如没装 `secret-tool`、没有桌面会话的钥匙串服务），账户照样能保存但不存密码，退回读环境变量 `DSH_MISHU_SECRET_MAIL_<编号>`。
  - 没用 DSH 自带的凭据服务：它默认是 `~/.dsh/.credentials.yaml`，一个只有本人可读写（0600）的**明文**文件。
  - 实测情况：macOS 已在真机上验证增、读、改、删，以及密码不落进任何文件；Windows 和 Linux 还没有真机验证。
- **第三方依赖**：只有 `imapflow`（IMAP 协议库），锁精确版本，并且选发布满两周的版本，不跟最新。DSH 安装插件时会自动给装进来的包加"最短发布时间"豁免，这道检查对插件不起作用，只能自己把关。

## 用户数据安全

秘书看到的是一个人最私密的东西：他在跟谁打交道、欠谁什么、哪天要交什么钱。这一节是硬性约束，新功能都要先对照它。分两条线。

### 一、开发和测试：真实数据不进仓库

- **仓库里的测试只用编造的数据。**`tests/fixtures/synthetic.ts` 在代码里造出一个虚构账号（`example-org`、`upstream-org`、`demo-*`），覆盖规则要处理的所有情况。它不是从真实数据改出来的。
- **真实录制只留在开发者本机。**`npm run record` 写到 `tests/fixtures/local/`，这个目录在 `.gitignore` 里。录下来的是开发者自己账号的数据，可能包括私有仓库、提交作者的邮箱、别人的账号，绝不提交，也不能拿来改写成提交的测试。
- **文档、注释、提交信息里也不放真实数据。**举例一律用虚构名字。
- **提交前扫描。**每次提交前，在要提交的文件里搜一遍开发者自己的仓库名、邮箱、主机名、本机路径。
- **npm 包不含测试。**`package.json` 的 `files` 只包括 `lib`、`cordis.patch.yml`、`README.md`。

### 二、产品：用户的数据

**存在哪里**

- 只存在用户自己的电脑：`~/.mishu/mishu.db`。在 macOS / Linux 上这个目录只有本人能读写（0700）；Windows 不支持这种权限设置，会忽略。
- 只存元数据和简短备注：通知的标题、仓库、理由码、你交代的事。不存邮件正文，不存 token。
- 卸载插件不会删它；要清除就删掉 `~/.mishu` 目录。

**数据去向**

| 去向 | 什么时候 | 送什么 |
|---|---|---|
| GitHub API | 每 15 分钟一次，以及你点"同步"时 | 用你自己的 token 发只读请求。标已读只有你把 `markRead` 改成 `on` 才会发 |
| DSH 当前用的模型（经"+AI"） | 你点某处的"+AI"，**再在新对话里按发送**时 | 这张卡片（或总结、报错、服务商说明）上已有的内容和相关通知标题。点"+AI"只是把这些文字放进新对话的输入框，不发送；你能看到、能改、能删，按了发送才发给模型。邮箱报错里只有服务器、端口、用户名和报错，**从不带密码** |
| DSH 当前用的模型 | 你在对话里让 agent 调用 `mishu_list`、`mishu_add`、`mishu_detail` 等工具时 | 工具返回的内容（简报、交代的事）会进入对话，跟对话里其他内容一样发给模型提供方。选本地模型（Ollama 等）就不出本机 |
| 你的邮件服务器（IMAP） | 每 15 分钟一次，以及你点"同步""现在收一次""测试连接"时 | 用你在设置页填的用户名和钥匙串里的密码登录，只读打开收件箱，只取最近几天未读邮件的信封（发件人、收件人、标题、时间）和 5 个邮件头，不取正文，不改任何东西 |
| 作者的服务器、统计、遥测 | 从不 | 没有这类连接 |

看板和 `/mishu` 命令的内容只在本机显示，不经过模型。

**谁能看到**

- 看板的接口走 DSH 自带的认证通道，只有登录了这台 DSH 的浏览器能调用。
- 同一个 DSH 里装的其他插件，技术上也能读到这些接口和记事本。这是 DSH 插件模型的边界，mishu 管不了。要在文档里如实告诉用户。

**日志**

- 只记数量和错误（几条通知、关了几件、哪一步失败），不记标题、备注和交代的内容。

**用户能控制的**

- `github.enabled: false` 关掉 GitHub；`markRead: off` 完全不碰 GitHub 上的已读状态。
- 想不让内容发给模型，就别在对话里让 agent 调 mishu 的工具，只用看板和 `/mishu`；或者把 DSH 换成本地模型。
- 删掉 `~/.mishu` 就清空全部数据。

### 以后接新功能的约定

- **邮件**（已做）：只读接入（`EXAMINE`）；只看信封和邮件头，不取正文；授权码放系统钥匙串。以后要交给模型判断时，还要能设置"永不送模型"的发件人或域名。
- **交给模型判断**：默认关闭，由用户主动打开；只送判断需要的字段，不送全文。
- **推送到手机**：默认只推标题。渠道的服务器（飞书、Telegram、Bark 等）会看到推送的内容，用户选渠道时要写明这一点。
- **任何新的数据去向**，都要先补进上面那张表，再写代码。

## 来源和顺序

1. **GitHub 通知**（第一版）：用 `/notifications` API，再按 subject 查 PR、issue、CI 的当前状态。
   - 注意：CI 类通知（subject 类型 `CheckSuite`）的 `subject.url` 通常是空的。要从标题里解析出工作流名和分支（如 "Nightly report workflow run failed for main branch"），再按仓库、工作流、分支查 Actions runs API。"已取代"和"已恢复"两类规则都依赖这一步。
2. **手动交代和周期事项**（第一版）：你说一句，秘书就记下（比如"护照明年 3 月到期"、"每月 15 号交房租"）。很多电脑外的事没有消息来源，只能这样进来。第一版只在 DSH 里交代；在手机上给推送机器人发一句话，等推送渠道接上以后再做。
3. **邮箱**：见上面的"邮件"一节。
4. **飞书**：消息、@我、审批、日程、任务（开放平台 API，长连接）。
5. **Telegram**：不做"读你账号的消息"。那要用 MTProto 登录个人账号，有封号风险，凭据也敏感。Telegram 只作为推送出口。
6. **以后**：主动检查型来源（证书和域名到期、云服务续费、API 余额、npm 安全告警、Dependabot），手机短信，Apple 日历和提醒事项。

用户需要秘书做的全部事情，包括电脑上的、电脑外的，以及暂时做不了的，见 [需求清单.md](需求清单.md)。

## 第一版

- **范围**：两个来源，**GitHub** 和 **手动交代 / 周期事项**。
  - GitHub：事项模型、规则、理由码、L0 自动归档、影子模式、纠错统计全部做上。
  - 手动交代：在 DSH 里用一句话交代。模型把它解析成结构化的事项（做什么、截止日期、周期、提前多久提醒），**先给你看解析结果，确认后再存**。
  - 周期事项：到期前按设定的提前量生成本期事项。你说"办了"，本期关闭，下一期按周期自动排上。
  - 提前量有默认值，可以改。比如证件提前 3 个月（办证需要时间），账单提前 3 天，生日提前 7 天（留出准备礼物的时间）。
- **输出**：左侧栏"小秘书"打开的整页看板（顶部总结 + 要你处理 / 我记着 / 替你办了三栏），以及 `/mishu` 文字简报。推送渠道定下来以后接上。
- **验收**：
  - GitHub：用编造的测试账号跑一遍（27 条通知，覆盖上表所有情况），结果是 **19 件事、6 件待处理，其余 13 件都已关闭且理由码正确**。
  - 开发者用自己真实账号录一份数据，在本机额外检查：每条通知都判断了、没有查失败的、每件关闭的事都有理由码。真实数据不进仓库。
  - 手动交代：说"护照 2027 年 3 月 10 日到期"，生成一个事项，2026 年 12 月 10 日开始提醒；说"每月 15 号交房租"，每月 12 号出现本期事项，说"交了"就关闭，下个月自动再出现；表述含糊（比如"下个月初"）时会追问，不乱猜。

## 命名

**选定：`dsh-mishu`**（2026-10-20 查过：npm 404 未占用，GitHub 没有同名仓库，插件市场没有同名或近似名）。

- 拼音命名，中文用户一看就懂"小秘书 = 替我盯消息、提醒我该做什么"。
- 短，`dsh plugin add dsh-mishu` 好敲好记。
- 搜索靠描述和 keywords 覆盖：描述里写全 **提醒、通知、待办、消息、收件箱、秘书、GitHub、邮件、飞书、Telegram**。

其他看过的候选：

- **npm 已被占用：**dsh-inbox（市场里也有同名）、dsh-todo、dsh-radar、dsh-brief、dsh-digest、dsh-reminder、dsh-alert、dsh-butler、dsh-pulse
- **能用但不如 mishu：**dsh-triage（中文用户不熟，市场里还有好几个 *-triage）、dsh-catchup（中文用户不直观）、dsh-pending / dsh-unread（市场里已有多个近似名）、dsh-daiban / dsh-tixing（会跟一堆待办和提醒插件混淆）

## 参考实现

- **插件结构**：cordis 插件，TypeScript；`src/core` 不依赖 DSH，`src/dsh` 是插件壳；用 `node:sqlite`；测试用 `node:test`。安装命令是 `dsh plugin --profile <name> add …`。测试只在独立的 profile 里做。
- **本产品独立**：代码和文档里不引用其他自研项目的内容。
- **全平台**：macOS / Windows / Linux 都要能跑。路径一律用 `node:path` 拼，`~` 展开用 `os.homedir()`；npm 脚本不用 `rm -rf`、`VAR=value` 这类只有 Unix shell 才认的写法；子进程（`gh auth token`）用 `execFile`，不走 shell。
- **双语**：中文 / English。配置项 `language`：`auto`（跟系统语言）、`zh`、`en`。秘书自己写的文字（GitHub 事项的标题和备注）两种语言都存，切换语言后旧事项也跟着变；你交代的原话照原样存。命令中英文都认。
- **发布**：npm 发布要你自己输 OTP。提交市场是给 awesome-dsh-plugin 提 PR，新增 `data/plugins/AIcivilization__dsh-mishu.yml`。

## 市场调研结论（2026-10-20）

awesome-dsh-plugin 的 6254 个插件里，**没有"从多个来源拉取 + 判断哪些要处理"的插件**；外部产品也没有现成的（多是 n8n / Zapier 模板，或者只做汇总不做判断）。可以借鉴思路的有：

- `Harzva/dsh-pr-guardian`：自己 PR 的"已处理"进度
- `delock/dsh-pr-board`：PR 分类（等我 / 等作者 / 可合并）
- `lumoping/dsh-todo-inbox`：待办加侧栏角标，最接近 mishu 的输出形态
- `zhengjy01/dsh-task-dispatcher`：只在有变化时通知
- `john-walks-slow/dsh-proactive`：定时唤醒、安静时段、每日预算
- dsh-feishucard：飞书卡片审批的交互方式
